## 4. 채택한 변경

### (a) KRW_1을 성과 계산에서도 제외 — `executor.py`

`total_all_krw`·`current_principal_krw`에서 제외 계좌의 보유·현금·매입금액을 차감.
계좌별 매입금액 추적(`krw_acc_purchase`)을 새로 추가했다. 이 두 값만 바꾸면 peak·
드로우다운·알파·원금이 전부 자동으로 제외 기준이 된다.

### (b) 빈 CSV 폴백 — `deposit_log.py`

```python
if path.exists():
    csv_events = read_events_from_csv(path, since=since)
    if csv_events:                    # 구간 내 기록이 있을 때만 채택
        return csv_events, "csv"
    # 없으면 아래 자동 감지로 폴백
```

수동 기록의 최우선 순위는 유지(가장 정확)하되, 안 적어도 자동 감지가 동작한다.

### (c) 부수 효과 — 환전 자동 감지 (설계상 핵심)

KRW_1과 USD는 **계좌번호가 같아**(`64378890-01`) KRW→USD 환전이 외부 입출금 API로는
잡히지 않는다. 그런데 **KRW_1 제외 기준 원금(매입금액+예수금)**으로 보면:

- KRW_1에 외부 입금 → 없는 계좌 안에서만 움직임 → 순유입 0 ✅ (성과 무영향)
- KRW_1 → USD 환전 → 없는 계좌에서 있는 계좌로 유입 → **순유입 = 환전액** ✅

즉 "굴리기 시작한 돈"만 정확히 입금으로 잡힌다. KIS 역산 백엔드(Δ원금 − 실현손익)가
이를 자동 감지하며, 실측으로 확인했다(첫 probe에서 기준차 -24,922,141원을 정상 검출).

### 9.1 후속 오류 — 수동 기록이 settlement 전에 소비됨 (같은 날, 사후 정정)

사용자가 "2,000만원 KRW_1→USD 환전, 10시 이후"라고 확인해줘서 `deposits.csv`에 수동 기록했는데,
바로 다음 자동 실행(08/19 03:01 USD)에서 이 기록이 peak에 +2,000만원으로 즉시 반영됐다. 문제는
**실제 계좌 잔고(total_all_krw)는 그 시점까지 전혀 늘지 않았다는 것** — 환전 자금이 아직
정산(settlement) 전이라 조회에 안 잡히는 상태에서 peak만 먼저 올라간 것. 그 결과 드로우다운이
가짜로 -8.25%(다음날 -9.62%)까지 찍힘 (레짐 Goldilocks·VIX 14.9로 실제 위기 신호 전혀 없었음 —
숫자만 보고도 이상 감지 가능했던 사례).

**교훈**: 수동/자동 불문하고 입출금 기록은 "이벤트가 있었다"가 아니라 "잔고에 실제로 반영됐다"를
확인한 뒤 넣어야 한다. 정산 지연이 있는 환전·이체는 하루 이틀 뒤 total_all_krw가 실제로
움직이는 걸 보고 나서 기록하는 게 안전하다 — 지금은 자동감지(§9 본문)가 있으니 정산되는 순간
알아서 잡아줄 것이므로, 정산 전 선제 수동 기록은 권장하지 않는다.

**복구**: `peak_krw`를 사고 전 값(233,780,221원)으로, `bench_spy_shares`를 사고 전 값
(189.63476987824774)으로 되돌림. 되돌리는 도중 **레이스 컨디션**도 발견됨 — 첫 번째 peak
수정(10:18) 당시 그날 10시 KRW 자동매매가 API 레이트리밋으로 아직 실행 중이었고, 그 작업이
나중에(10:21) 끝나면서 자기가 시작할 때 읽었던 옛 peak 값으로 덮어써버려 수정이 한 번
유실됐다. `ps aux`로 실행 중인 run.py가 없는 걸 확인한 뒤 재적용해서 최종 확정.
최종 확인: peak 233,780,221원 / bench_spy_shares 189.635주 / 실제 드로우다운 -1.89%.

**여전히 남은 위험**: §6 경고(제외 계좌 수동 매매 시 오염)는 그대로 유효하다. KRW_1에서
매매하면 이 안전장치로도 못 잡을 수 있으니, 그런 경우는 여전히 `deposits.csv` 수동 기록을
